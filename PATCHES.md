### 5. Copy CLAUDE.md fragments instead of symlinking on Windows

- **File:** `src/claude-md-compose.ts` (`syncSymlink` → `syncFragment`, plus `hostSource` on the desired-fragment map)
- **Summary:** On `win32` hosts, inline the host file content (`fs.readFileSync` + `writeAtomic`) instead of `fs.symlinkSync`. Composition runs per-spawn so the inlined copy is never stale.
- **Why:** The upstream design uses symlinks whose targets are container-side absolute paths (`/app/CLAUDE.md`, `/app/src/mcp-tools/<x>.instructions.md`), valid inside the container via RO mounts, dangling on the POSIX host. On Windows, MSYS2/Git-Bash (NSSM service env, or any Node-via-Bash spawn) rewrites these POSIX-absolute targets at symlink-creation time to `/d/app/...`, which Docker then exposes as `/mnt/host/d/app/...` inside the container — permanently broken. Impact: without this patch the composed `groups/<folder>/CLAUDE.md` imports 1 broken `.claude-shared.md` + 5 broken `.claude-fragments/module-*.md` links, meaning the agent never sees the shared `container/CLAUDE.md` (non-negotiable rules, skills overview) nor the MCP tool instructions (agents, core, interactive, scheduling, self-mod).
- **Exit condition:** Upstream changes the composition to write content directly (not symlinks), or Node/Windows stops translating POSIX-absolute symlink targets.
- **Lines:** ~18 (platform branch in `syncFragment` + `hostSource` plumbing on 3 call sites).

### 8. Container-side MCP fail-fast probe (`mcp-health.ts` + SDK init/mid-session guards)

- **Commits:** `efc651b` (PR #17, HTTP probe), `8eac0ba` (PR #30, SDK init guard, issue #27 branch 1), follow-up mid-session detection (issue #27 branch 2).
- **File:** `container/agent-runner/src/mcp-health.ts` + integration in `index.ts` and `poll-loop.ts`; SDK init + mid-session guards in `container/agent-runner/src/providers/claude.ts` (`translateEvents`); `mcp_tool_missing` event handling in `poll-loop.ts` (`processQuery`).
- **Summary:** Three complementary checks. (a) At container boot AND before each turn, probe required `mcp-remote` HTTP MCP endpoints with a JSON-RPC `initialize` call. Halt the container (boot) or block the turn (per-turn) if the chain is unreachable. (b) When the Claude SDK emits its `system/init` message, inspect `mcp_servers[].status` and throw only on **terminal failure** statuses (`'failed'`, `'needs-auth'`). `'pending'` is the normal mid-handshake state — the SDK reports it whenever async MCP connections are still completing — so rejecting it would block every healthy startup. `'connected'` and `'disabled'` are accepted; missing entries are logged but not fatal. (c) Mid-session: when the SDK auto-injects a `tool_result` with `is_error: true` and `"No such tool available: mcp__<required-server>__*"` (typical post-compaction failure on z.ai's Anthropic-pretend endpoint), `detectMissingMcpTool` emits a `mcp_tool_missing` provider event. The poll-loop aborts the turn, clears `continuation:claude`, and writes a single user-visible message asking the user to resend — the next inbound respawns with a fresh init, restoring the registry.
- **Why:** Silent partial-degraded operation is the failure mode that triggered this code. Three distinct silent-failures observed: (a) `roo-state-manager` 404 masked by `sk-agent` still working, agent kept replying as if everything was fine (PR #17 fix). (b) On z.ai's Anthropic-compatible endpoint, the chain probe passes (HTTP 200 from `mcp-tools.myia.io`) but the SDK reports `mcp_servers[].status='failed'` at init for one or more required servers — every `mcp__<server>__*` call then returns "No such tool available" while the bot keeps replying "Dashboard MCP DOWN" indefinitely (PR #30, issue #27 branch 1). (c) Even when init is clean, the SDK loses its tool registry mid-session after auto-compaction on z.ai (22 occurrences observed in session 412a71e3 between 2026-04-24 and 2026-05-01, all post `compact_boundary`). Without branch 2, the bot would reply "MCP down" to every subsequent message until manual container-kill — happening "several times a day" per operator. The HTTP probe alone is insufficient at any phase; only the SDK's own registry signals (init `mcp_servers[]` + per-turn `tool_use_error` blocks) reflect what tools are actually callable.
- **Exit condition:** Upstream adds container-side MCP health probes covering all three phases (HTTP + SDK-init + mid-session tool_use_error) in the agent-runner provider abstraction, or our cluster moves off `mcp-remote` and z.ai Anthropic-pretend to a transport that doesn't lose tool registry post-compaction.
- **Lines:** ~150 (module + integration + tests) + ~25 (SDK init guard) + ~80 (mid-session detection + event plumbing + tests).

### 25. Serialize follow-up pushes in container poll-loop

### 27. Idle-with-pending watchdog in container poll-loop

- **File:** `container/agent-runner/src/poll-loop.ts` (`processQuery` — new `lastResultAt` timestamp, set on every `result` event; new `idleHandle` `setInterval` paired with `clearInterval` in the existing finally block).
- **Summary:** A second per-query watchdog complementing PATCH #26. Every `IDLE_CHECK_INTERVAL_MS=5s`, if `awaitingResult === false` (turn is done — outside #26's domain) AND `messages_in` holds at least one `trigger=1` non-system row in `pending` state AND `Date.now() - lastResultAt > IDLE_WITH_PENDING_TIMEOUT_MS=45s`, force `query.end()`. - **Why:** PATCH #26 gates on `awaitingResult === true` — it only fires while the loop is expecting a result from the SDK. Three observed failure modes converge on this gap:
  - The async `pollHandle` IIFE inside the inner setInterval can latch `pollInFlight = true` if `applyPreTaskScripts` hangs (dynamic import + filesystem I/O on the host bind mount). No more pushes happen until the IIFE somehow resolves.

  - The previous turn ended with `<internal>…</internal>`-only output (line 965 logs `WARNING: agent output had no <message to="..."> blocks`). On the user's POV the bot stopped responding; the for-await is still iterating but no new events come, and pollHandle's push depends on `awaitingResult === false` which it is — yet the push silently fails to reach the SDK.
  Operator feedback (2026-05-12): "régulièrement je m'adresse aux 2, et il n'y a que Hermes qui répond". The recurrence rate makes this a top-3 reliability bug for the cluster-manager group. Hermes (peer install with one query per message) does not see this symptom — confirms it's the push-mode/long-lived-query interaction with z.ai's Anthropic-pretend endpoint that NanoClaw uses. Force-ending the query is preferable to a hard `query.abort()`: the SDK closes the stream cleanly on the host side, the outer loop's next iteration spawns a fresh query with the same continuation, and the backlog gets processed without any user message lost.
- **Exit condition:** Upstream poll-loop adopts an inbox-pressure-aware watchdog covering the idle-with-pending gate, OR the SDK exposes a per-stream liveness probe the container can poll directly, OR pollHandle is restructured so its async IIFE cannot latch `pollInFlight=true` (e.g. by running pre-task scripts in a worker with a hard timeout).

### 29. Soften the per-turn required-MCP fail-fast gate (retry instead of drop)

- **File:** `container/agent-runner/src/poll-loop.ts` (fail-fast gate in `runPollLoop` — `resetProcessingAcks` instead of `markCompleted`, throttled notice via `lastBlockedNoticeAt`, `BLOCKED_RETRY_BACKOFF_MS` sleep before `continue`); `container/agent-runner/src/mcp-health.ts` (`probeMcpRemoteCached` caches successes only).

### 41. Re-check the continuation-rotation guard mid-life (idle), not just at startup

- **File:** `container/agent-runner/src/poll-loop.ts` — new exported pure helper `evaluateMidLifeRotation`, a `ROTATE_CHECK_INTERVAL_MS` constant, a `lastRotateCheckAt` bookkeeping var in `runPollLoop`, and a call in the idle branch (`messages.length === 0`). Tests in `poll-loop.test.ts`.
- **Summary:** The provider's `maybeRotateContinuation` guard (Claude: rotate the session when its transcript `.jsonl` exceeds `CLAUDE_TRANSCRIPT_ROTATE_BYTES`, default 12 MB, or the age cap) is evaluated **once**, just before the poll loop. This patch re-evaluates it while idle — throttled to once per `ROTATE_CHECK_INTERVAL_MS` (60 s) — so a session whose transcript crosses the cap *between* tours is rotated to a fresh transcript before the next tour resumes it. On a hit it drops the continuation (the same reset the manual zombie recovery performs), pre-emptively. Idle is chosen because the probe renames the live `.jsonl` aside, which is only safe when no query holds it.
- **Why:** The `#2177` "zombie-heartbeat" wedges have two classes. The *bunching* class (two proactive tours claimed in one turn) is addressed by patch #26's 240 s watchdog + host de-bunching. The *accumulation* class is not: a container that stays up for hours (heartbeat keep-alive #30 keeps it alive precisely so it isn't reaped hourly) keeps resuming and appending to one transcript. The SDK only sometimes forks a fresh session on compaction; when it doesn't, the `.jsonl` grows unbounded. Wedge #7 (2026-07-16) reached **21 MB** — well past the 12 MB cap that would have rotated it at startup — but the guard never re-ran mid-life, so the SDK query died mid-thrash and the file-touch heartbeat kept ticking, so the heartbeat reap never fired → silent multi-hour wedge, manual recovery required. This patch closes that gap by making the existing, already-tested guard fire during the container's life, capping transcript growth below the wedge zone automatically.
- **Scope caveat:** Prevents the *accumulation* wedge (transcript → 21 MB), not the *single-catastrophic-tour* wedge (a turn that crosses the cap and dies before returning to idle) — patch #26's watchdog covers that timing. Does not reduce per-tour compaction thrash itself (the deeper `poids-par-tour` lever); it bounds the cumulative bloat that thrash produces.
- **Exit condition:** Upstream makes the SDK reliably fork a fresh session on compaction (so no single transcript grows unbounded), or `maybeRotateContinuation` is moved into the loop upstream.
- **Lines:** ~20 (helper + idle-branch call + constant/var + comments)

### 45. Channel adapter: self-heal a transient setup failure, and never silently discard outbound

- **Files:** `src/channels/channel-registry.ts` (throw instead of silent `return` in `createChannelDeliveryAdapter().deliver`; new `retryAdapterInBackground` + `BACKGROUND_RETRY_DELAY_MS` + `shuttingDown` guard, hooked into `initChannelAdapters`'s catch and `teardownChannelAdapters`).
- **Summary:** Two independent defects that compounded into a five-day silent outage. **(a) Permanent death:** `initChannelAdapters` retries a failed `adapter.setup()` only on the inline `SETUP_RETRY_DELAYS_MS` budget (2s/5s/10s ≈ 17s total); a network outage that outlasts it logs `Failed to start channel adapter` and abandons the channel **for the entire process lifetime**. No re-arm, no health check. **(b) Silent discard:** with no adapter registered, `createChannelDeliveryAdapter().deliver` logged a `warn` and `return`ed `undefined` — which reaches `deliverMessage` as a *successful* completion, so `delivery.ts` logged `Message delivered`, `clearOutbox()`ed the attachments and `markDelivered()`ed the row. Every outbound message was destroyed while the logs affirmed delivery; the only tell was `platformMsgId=undefined`. Fix: setup failures with `NetworkError` now retry in the background every 60s until they succeed (non-network errors — bad token, misconfig — still fail fast, so we never spin on something a retry cannot fix), and the no-adapter delivery path throws, routing the message into the existing 3-attempt retry → loud `Message delivery failed permanently, giving up` ERROR.
- **Why:** 2026-07-21→25 incident, root-caused firsthand. `[00:47:48.205] ERROR Failed to start channel adapter channel="telegram" err={type:"NetworkError", message:"Network error calling Telegram deleteWebhook"}` — a boot-time blip. For the next five days the host ran "healthy" with **no Telegram adapter in `activeAdapters`**: outbound was marked delivered and thrown away (9662 `Message delivered` lines, all `platformMsgId=undefined`), and inbound had **no `getUpdates` poller at all** — nothing routed after `2026-07-20T09:46:55Z`, the owner's last message. This is orthogonal to the autocompact-thrash family (#40/#41 here, plus #42–#44 in flight): the container, heartbeat, transcripts and rotation were all genuinely fine. Surveillance kept returning SAIN because it scored `messages_out` rows as "real work" — proving the agent *produced* output, never that it *landed*. Defect (b) is what made defect (a) invisible; the codebase already documents the correct principle one function away, at `delivery.ts:317` ("Failures throw — unlike a silent `return`, an Error falls into the retry path […] instead of marking it delivered when nothing was actually delivered"), and the pre-existing registry test already *described* the intended behavior as "drop into the retry path" while asserting the buggy resolve.
- **Exit condition:** Upstream adds a supervised/self-healing channel-setup path (periodic re-arm or health check) **and** treats a missing adapter as a delivery failure rather than a silent success. Re-evaluate at next sync; the throw half may land upstream independently of the retry half.
- **Test:** `src/channels/channel-registry.test.ts` — `background retry after a transient setup failure [PATCH-myia #45]` (recovers after outlasting the inline budget, then delivers; non-network error gives up fast), plus the updated cross-identity test now asserting `rejects.toThrow`.

### 42. Autocompact-thrash self-heal (drop continuation on thrash, both error shapes)

- **Files:** `container/agent-runner/src/poll-loop.ts` (new `THRASH_RE` const; `processQuery` result path; `QueryResult.thrashCleared` field + return; `runPollLoop` handler after `mcpRegistryLost`), `container/agent-runner/src/providers/claude.ts` (`STALE_SESSION_RE`).
- **Summary:** "Autocompact is thrashing" surfaces in two shapes: a *result error* (`isError=true` result event) or a *throw* (`Claude Code returned an error result: Autocompact is thrashing…`). Neither path previously touched the continuation, so every subsequent turn resumed the same bloated session and re-thrashed — an infinite loop (bot "alive but producing no work"). Result shape: `processQuery` matches `THRASH_RE = /autocompact is thrashing/i` on an error result, signals via the new `QueryResult.thrashCleared` flag, and `runPollLoop` clears the continuation — same shape as the existing `mcpRegistryLost` signal. This patch reacts to the thrash *signal itself*, regardless of transcript size or container persistence. Proactive layers (config, not code): `.env CLAUDE_TRANSCRIPT_ROTATE_BYTES=4194304`, and the review-task prompt's DIFF BUDGET + max-2-PRs-per-cycle bound (ops-side, session DB).

### 46. Make `add_reaction` work on Telegram, and stop retrying a deterministic rejection

- **Files:** `src/channels/chat-sdk-bridge.ts` (`isReactionInvalidError`, `substituteReaction`, wired into the reaction path), `src/delivery.ts` (defense-in-depth net, mirroring #21).
- **Summary:** Two defects, one root. (a) The agent-facing contract is a **shortcode**, by design — `container/agent-runner/src/mcp-tools/core.instructions.md:23` states `emoji` is "the shortcode name … not the raw character" and offers `white_check_mark` as the example for "done". The Telegram adapter resolves that to ✅ via `toTelegramReaction` → `defaultEmojiResolver`, and Telegram does **not** accept ✅ in its fixed reaction allowlist. So the documented happy path failed on every use, while the same shortcode works fine on Slack. Measured on this install (`outbound.db`, 70 reactions, 100 % shortcodes): `eyes`→👀 and `thumbs_up`→👍 land; `white_check_mark`, `warning`, `x` never did. (b) That rejection (`Bad Request: REACTION_INVALID`) is **deterministic**, but it bubbled to the generic retry path — an existing test even asserted it should. Result: 11 permanent abandons × 3 attempts = 33 wasted API calls and 11 `Message delivery failed permanently` ERROR lines, all benign. Fix substitutes only where the replacement preserves the speech act (`white_check_mark`/`check`/… → 👍, `x` → 👎, `thought_balloon` → 🤔), leaves anything without an honest equivalent alone (⚠️ has none in Telegram's set), and swallows the rejection instead of retrying it. Substitution is gated on `adapter.name === 'telegram'` so Slack/Discord are untouched, and emits raw characters so it does not depend on the adapter's shortcode vocabulary (its `EMOJI_NAME_PATTERN = /^[a-z0-9_+-]+$/i` does not match a raw emoji, which then passes through untranslated).
- **Why:** The retry waste is minor; the log damage is not. `Message delivery failed permanently` is the highest-severity delivery signal the host emits, and salting it with known-benign entries trains the operator (and the surveillance playbook) to skim past it — the same erosion that let the 2026-07-21 silent-adapter outage run five days. Cosmetic failures must not occupy the channel reserved for real ones.
- **Exit condition:** Upstream teaches the shortcode contract about per-platform reaction allowlists (or the Telegram adapter substitutes/rejects locally), and treats a platform-level emoji rejection as non-retryable. Then both halves drop. Raise upstream at the next sync — the instructions file and the adapter are both upstream-owned, so this is a genuine upstream bug, not a local preference.
- **Lines:** ~75 (incl. comment blocks and the substitution table)
